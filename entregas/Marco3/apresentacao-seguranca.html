Segurança no balanceamento de filas

Como protegemos a comunicação entre os ESP32, o broker MQTT e os serviços Python: criptografia, identidade por componente, menor privilégio, gestão de segredos e validação dos dados.

Caio Castro Miranda · João Pedro de Brito Tomé · João Victor Braga · Jaime da Cruz

Ponto de partida

O que poderia dar errado

Escuta no enlace

O ESP32 usa a rede aberta Wokwi-GUEST. Sem criptografia, qualquer um na rota leria contagens e estados.

Dispositivo falso

Um broker anônimo deixaria qualquer cliente publicar chegadas e encher a fila artificialmente.

Componente fazendo demais

Se todos tivessem a mesma senha, o painel de LEDs poderia publicar recomendações ou apagar pessoas da fila.

Senha no Git

Credenciais embutidas no código vazariam no primeiro git push.

Dados inconsistentes

Reentregas do MQTT, tópicos trocados ou payloads inválidos distorceriam a ocupação.

Credencial no navegador

Uma página que fala MQTT direto exporia a senha a quem abrisse o código-fonte.

Arquitetura

Tudo passa por um broker com TLS

Camada 1 · Confidencialidade e integridade

MQTT somente sobre TLS

  • A porta sem criptografia 1883 foi removida. O único listener é 8883, com TLS 1.2 ou superior (no log, os clientes Python negociam TLS 1.3 e o ESP32 negocia TLS 1.2 com ECDHE).
  • Usamos uma CA própria de desenvolvimento, que assina o certificado do broker para localhost, host.wokwi.internal e 127.0.0.1.
  • Todo cliente verifica o certificado: o Python usa ssl.create_default_context(cafile=ca.crt) e o ESP32 usa tls.setCACert(MQTT_CA).
  • O broker escuta apenas em 127.0.0.1: ninguém da rede local consegue se conectar a ele.
# broker/mosquitto.conf
listener 8883 127.0.0.1
allow_anonymous false
password_file .local/mqtt/mosquitto.passwd
acl_file broker/mosquitto.acl
certfile .local/mqtt/broker.crt
keyfile  .local/mqtt/broker.key
tls_version tlsv1.2

Criptografia · Infraestrutura de chaves

A cadeia de confiança

CA

CA:TRUE, uso só para assinar certificados (keyCertSign, cRLSign), validade de 10 anos. A ca.key nunca sai do computador nem vai para o ESP32.

Broker

CA:FALSE, uso serverAuth, nomes alternativos (SAN) para localhost, host.wokwi.internal e 127.0.0.1. Validade de 825 dias, até janeiro de 2029.

Por que é seguro distribuir a CA

O ca.crt contém só a chave pública. Ele serve para verificar, não para assinar. O firmware intruso também o tem, e mesmo assim o broker o recusa.

Criptografia · Handshake observado

O que o broker negociou de verdade

# clientes Python (log do broker)
negotiated TLSv1.3
cipher TLS_AES_256_GCM_SHA384

# ESP32 consumidor no Wokwi
negotiated TLSv1.2
cipher ECDHE-RSA-AES256-GCM-SHA384
Parte da cifraFunção
ECDHECombina uma chave nova a cada conexão, e ela nunca trafega pela rede.
RSAO broker assina o handshake e prova que tem a chave do certificado.
AES-256-GCMCifra os dados e detecta qualquer byte alterado no caminho.
SHA384Deriva as chaves da sessão (HKDF ou PRF).

Sigilo direto: mesmo que a broker.key vaze no futuro, quem gravou o tráfego antes não consegue decifrá-lo, porque as chaves de sessão eram efêmeras.

Criptografia · Senhas

A senha nunca é guardada em texto no broker

  • mosquitto_passwd guarda um hash PBKDF2-HMAC-SHA512 com sal, não a senha.
  • O sal é aleatório para cada usuário: duas senhas iguais geram hashes diferentes.
  • O PBKDF2 repete o hash muitas vezes, o que deixa o ataque de força bruta mais lento.
  • Com 192 bits de entropia, adivinhar a senha é inviável, mesmo que alguém consiga copiar o mosquitto.passwd.
  • A senha só trafega dentro do túnel TLS, nunca em claro.
# .local/mqtt/mosquitto.passwd (formato)
produtor:$7$<iterações>$<sal>$<hash>
consumidor:$7$...
processador:$7$...
validador:$7$...
observador:$7$...

# $7$ = PBKDF2 com SHA-512
Camada 2 · Autenticação

Uma identidade para cada componente

  • allow_anonymous false: sem usuário e senha, o broker recusa a conexão.
  • São cinco identidades: produtor, consumidor, processador, validador e observador.
  • Cada senha é aleatória (openssl rand -hex 24, 192 bits). No broker fica só o hash gerado pelo mosquitto_passwd.
  • Os dois ESP32 têm senhas diferentes: se o firmware de um vazar, o outro continua protegido.
# mqtt_config.py — usado por todos os clientes Python
contexto_tls = ssl.create_default_context(cafile=str(ca))
contexto_tls.minimum_version = ssl.TLSVersion.TLSv1_2
client.username_pw_set(usuario, _senha_de(papel))
client.tls_set_context(contexto_tls)

// main.cpp — ESP32 de entrada
tls.setCACert(MQTT_CA);
mqtt.begin("host.wokwi.internal", 8883, tls);
mqtt.connect("wokwi-sensores", "produtor", MQTT_SENHA);

O processador é o único que pode publicar o estado da fila. Mesmo que um ESP32 seja comprometido, ele não consegue mudar o semáforo de outro componente.

Camada 4 · Gestão de segredos

Nenhuma senha no repositório

Pasta isolada

Senhas, chaves e certificados ficam em .local/mqtt, com permissão 0700 na pasta e 0600 nos arquivos, e o Git ignora a pasta.

Geração por script

configurar-seguranca.sh cria a CA, o certificado do broker e as cinco senhas. O script se recusa a sobrescrever uma configuração existente.

Evolução sem quebrar

--adicionar-consumidor e --adicionar-validador incluem um papel novo, e --renovar-certificados troca o certificado, tudo sem mudar as outras senhas.

Firmware sem segredo versionado

preparar-wokwi.py gera segredos.h e segredos_consumidor.h, cada um só com a senha do seu papel e a CA. Os dois arquivos estão no .gitignore.

Navegador sem credencial

A página de validação conversa só com o servidor Python local, e é o servidor que publica no MQTT como validador.

Camada 5 · Integridade dos dados

Desconfiar do que chega

Processador

  • Confere se o filaId do payload é igual à fila do tópico.
  • Só aceita os tipos contagem, validacao e heartbeat, e o resultado precisa ser aprovado ou reprovado.
  • Descarta eventos repetidos pelo eventId, com INSERT OR IGNORE no SQLite. Assim, uma reentrega do QoS 1 não conta a mesma pessoa duas vezes.
  • Decide se o enlace está vivo pelo relógio do próprio processador, nunca pelo horário que o dispositivo informa.

Servidor de validação e consumidor

  • O HTTP escuta só em 127.0.0.1:8000.
  • O POST aceita no máximo 1 KB, só fila-a ou fila-b, e responde 409 se a fila estiver vazia.
  • O eventId é gerado pelo servidor (uuid4), não pelo navegador.
  • O ESP32 consumidor só aplica um estado se o tópico e o filaId coincidirem.
Evidências

Como verificamos

$ python3 broker/testar-acl.py
ACL de leitura: processador recebeu;
produtor não recebeu. OK

# log do broker (16/10/2026)
New client connected ... u'validador'
Client ... negotiated TLSv1.3
  cipher TLS_AES_256_GCM_SHA384
wokwi-consumidor ... u'consumidor'
Client ... negotiated TLSv1.2
  cipher ECDHE-RSA-AES256-GCM-SHA384
  • ACL de leitura: o mesmo dado chega ao processador e é bloqueado para o produtor.
  • Sem usuário: um cliente anônimo recebe Connection Refused: not authorised.
  • Firmware sem a chave: o ambiente intruso tem a CA, mas uma senha inventada, e o broker o recusa com o retorno 5 (não autorizado). Verificamos que a senha real não está no binário dele.
  • Só leitura: quando o observador tenta publicar uma contagem, o broker descarta a mensagem sem avisar, e ela não chega ao processador.
  • TLS: o Python negocia TLS 1.3 e o ESP32 consumidor negocia TLS 1.2 com ECDHE, ambos com AES-256-GCM.
  • Segredos: git check-ignore confirma que .local/ e os arquivos segredos*.h estão fora do controle de versão.

Transparência

  
Limites conhecidos e próximos passos

  

    
CA de desenvolvimento
A CA é autoassinada e só faz sentido na demonstração. Em produção, o certificado precisa vir de uma CA gerenciada, com renovação automática.

    
Senha dentro do firmware
Quem tiver acesso físico ao ESP32 consegue ler a flash. A evolução é usar a criptografia de flash do ESP32 ou certificado de cliente (mTLS).

    
Dados em repouso
O SQLite não é cifrado; o TLS protege só o trânsito.

    
Payload malformado
O processador não trata JSON inválido vindo de um cliente autenticado. A ACL limita quem pode publicar, mas falta um try no parser.

    
Broker apenas local
Para levar o broker a outro host, é preciso emitir um certificado com o novo nome e abrir o listener, sem nunca desligar a verificação TLS.

  






  
Resumo

  
Defesa em camadas

  

    
1 · TLS
Ninguém lê ou altera mensagens no caminho.

    
2 · Identidade
Cinco usuários com senhas fortes e distintas, e nenhum acesso anônimo.

    
3 · ACL
Cada componente faz só o que precisa.

    
4 · Segredos
Ficam fora do Git e do navegador e são gerados por script.

    
5 · Validação
O tópico precisa bater com o payload, eventos repetidos são descartados e as entradas são limitadas.

  

  
Se um componente for comprometido, o estrago fica restrito ao papel dele.
